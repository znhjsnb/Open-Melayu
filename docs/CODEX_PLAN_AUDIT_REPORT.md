## 4. Linux、分片、词表与打包

### 4.1 Ubuntu 包与启动方式

`python3-bs4` 是 Noble 的真实系统包，版本目录列为 `4.12.3-1`，依赖系统 Python 和 SoupSieve；这段脚本没有调用 pip。**apt 安装不会因 PEP 668 的 externally-managed-environment 机制被拒绝**。该机制约束的是 pip 等 Python 专用安装器修改系统管理的 Python 环境。无需添加 `--break-system-packages`。[Ubuntu 包目录](https://packages.ubuntu.com/noble/python3-bs4)、[PyPA 规范](https://packaging.python.org/en/latest/specifications/externally-managed-environments/)

仍需在目标镜像检查 apt 源、DNS、TLS、包锁和实际导入。`python3-urllib3` 并非此 worker 所需：代码使用标准库 `urllib.request`。依赖阶段的 `apt-get update ... && apt-get install ...` 还有一个 shell 陷阱：`set -e` 不保证在 `&&` 左侧命令失败时退出；update 失败可能跳过 install 后继续执行。应拆开命令并显式处理失败，保留可见的错误状态。

脚本文件当前为 LF、无 UTF-8 BOM，首行是正确的 `#!/bin/bash`；上传链路仍需保留这些字节。普通 cloud-init user-data shell 脚本在实例级执行一次，不等于每次重启都自动恢复爬取或 HTTP 服务。应将安装与运行分离，给 worker 和下载服务配持久监督、重启策略、日志及健康检查。[cloud-init 脚本执行说明](https://docs.cloud-init.io/en/latest/explanation/format/user-data-script.html)

### 4.2 主机名认领结果

以下为按源码推演，未在本机运行 Bash 成功：

| hostname | 当前结果 | 审查意见 |
| --- | --- | --- |

| `spider-01` | Bash 运算把 `01` 当八进制 1；Python `int('01')` 得到 1；包名却保留 `shard_01.tar.gz` | 不会因此自动报错，但下载器若约定 `shard_1.tar.gz` 会不一致 |

| `region2-spider-5` | 提取第一个数字 2，领取第 2 片 | 不是约定的完整命名校验 |
| `spider-08` | Bash 前导 0 数值含非法八进制数字，算术展开出错 | 非法名必须在算术前拒绝 |

最小修正可只接受完整的 `^spider-([1-5])$`；若必须支持前导零，先严格校验，再显式十进制转换和规范化包名。还应核验 Vultr 实际传入的是系统 hostname 而非仅控制台 label。汇总端必须检查分片编号唯一，不能仅凭“收到五个包”验收。

内嵌 Python 的通用分片公式本身正确：对 15,000 个输入产生 `[0,3000)`、`[3000,6000)`、`[6000,9000)`、`[9000,12000)`、`[12000,15000)`，每片 3,000。方案中的边界应采用这样的半开区间，避免误解成两片共有第 3,000 条。只有**相同的有序词表版本 + 唯一正确片号**才能保证不重不漏。

### 4.3 候选词表的实际检查

本地 `data/candidate_pool_15k.json` 为 **15,000 条、15,000 个不同词，全部小写，NFC + casefold 后无冲突**。现有 Gist 上传 payload 中的文本也有 15,000 行，顺序与该本地候选池完全一致：

```text
UTF-8 bytes: 117743
SHA-256: f31242e1dc4d37aa0574f8d8ef4b3aeac0babaec2b1b4b380e9d5771a0ab50a2
```

**这不是远端指定 revision 的校验结果。** raw 下载和 Gist 页面访问本次均未成功；无法证明上述 payload 已原样发布到给定 revision。部署前必须从可信渠道取得远端实际内容，与确认后的预期哈希比对。词表固定在 revision 路径是有益设计，但脚本没有对内容作任何校验。

`curl -sL` 默认不会将 404/500 当作传输失败，`set -e` 因而挡不住错误响应体。即使 HTTP 200，也须验证正文。建议使用 `--fail --show-error --location`、连接/总时限和有限重试，再验证固定词数、唯一性、字符与文件名规则。完整验证前不启动任何词条请求。[curl 官方手册](https://curl.se/docs/manpage.html)

### 4.4 tar 是否必然出错

`tar -czf ... --exclude=... *.json` 在当前目录中有正常可见 JSON 文件、使用 GNU tar 的前提下，可以把文件直接放在包的根目录。**没有额外父目录不是缺陷，普通情形不会因为这条通配符命令必然漏掉根目录 JSON。** `*.json` 本来也不会匹配 `.tar.gz` 或 `status.txt`，这两个 exclude 在当前输入模式下基本冗余。

但零 JSON 时，默认 Bash 将未匹配的 `*.json` 原样传给 tar，tar 会报找不到文件；隐藏的 `.xxx.json`、子目录 JSON 也不在这个模式内。当前本地候选池没有前导 `.` 或 `-` 的词，因此不能把隐藏文件或选项名风险说成已发生。更实在的问题是：脚本不按 manifest 限定输入，重跑工作目录里的旧 JSON 可能混入；错误缓存同样会被打包。

包在 HTTP 服务目录中直接生成，客户端可能在压缩结束前下载。应按本片有效记录清单在服务目录外构建临时包，检查成员、数量和 SHA-256 后原子移动进去，最后发布 READY。`COMPLETED` 在压缩之前出现，不能代替 READY。建议包内含分片 manifest、来源版本和各文件哈希；0 记录或有错误时明确标 PARTIAL/FAILED，不能当完整交付。

## 5. 缓存正确性、解析与失败恢复

### 5.1 已复现的行为

| 离线输入/故障 | 当前 worker 的实际结果 | 为什么不合格 |
| --- | --- | --- |
| HTTP 200、维护页、没有 tab-pane | 写入 `found_in_prpm=false` 的 JSON，返回 `ok`，内部 `found_count` 增加 | 网络传输成功被混作抓取成功，未证明该词确无记录 |
| 三次 HTTP 503 | 发出 3 次请求，睡眠为 1、2 秒，写 `error`；最后状态仍为 `COMPLETED` | 完成遍历与完成有效缓存混淆 |

最后两项合成 DOM 变化测试证明的是解析器边界，不宣称 PRPM 现网恰好采用该结构。现有两批说明已记录音节、词典来源、交叉词条人工补核需求，不能把当前抓取器等同于已验证的全自动词典解析器。

在检查开始时刻记录的本地缓存快照为 **316 个 JSON：234 个 found 标志、26 个 not-found 标志、56 个含 error**。这只是字段统计，**不等于 234 个已人工验证的官方词条**；缓存期间持续增长，无法视为锁定的一致性快照。完整记录与 UTC 时间在证据 JSON 中。有效缓存远少于“目录文件数”。

### 5.2 必须采用的状态和发布语义

至少区分 `pending / in_progress / ok / verified_not_found / retryable_error / parse_error`。`ok` 应要求目标词头、来源与必要字段通过验证；`verified_not_found` 要有正常搜索页及明确无结果证据，不能由空解析推断。少见词、口语词没有 PRPM 记录是正常可能性，不可因此要求模型捏造官方资料。

每条记录保存请求词、实际词头、来源 URL、获取时间、HTTP 状态、解析器版本和证据摘要/哈希。错误记录不能冒充正常缓存；解析损坏文件必须重新处理。写入采用同目录临时文件完成后 `os.replace`，避免进程中断或本地并发读取半个 JSON。持久任务清单须记录尝试数、上次错误和下次可重试时间。

`fut.result()` 没有单项兜底；最终写 error 文件也在保护范围之外。磁盘满、权限错误或不合法路径会让异常传到主循环并中止 worker。外层要登记失败而不是丢失整个分片状态；严重存储错误应明确失败退出。状态文件也应原子写，区分已尝试、有效命中、已证实无词条、错误及待处理数量。

## 6. 网络隔离、站点压力与下载安全

### 6.1 主力 IP 的保护边界

当五个 VPS 使用各自公网出口，且没有配置到主力东京节点的代理/隧道路由时，VPS 发出的 PRPM 请求通常不会以 `45.32.36.128` 为源地址。本地经东京节点下载 VPS 成果，也不等同于东京节点访问 PRPM。这个隔离方向合理。

但脚本注释不是运行时路由证明：`urllib.request` 可受系统代理环境影响，VPS 也可能有额外路由配置。上线前应检查受控的出口 IP、代理配置和到 PRPM 的请求来源；不得复用主力节点作失败重试代理。

更直接的缺口在本地：`prpm_continuous_crawler.py` 显式实现直连失败后回退 `127.0.0.1:7897`。审计期间缓存数量和进度文件多次增加，说明有外部写入活动；进程查询被宿主拒绝，因此本报告不声称已识别具体 PID，也不能确认每个请求实际走了代理。**能够确认的是“仅部署五台新 VPS”并未消除旧本地路径，100% 隔离没有成立的验证依据。**

迁移验收应包括识别并关闭旧抓取进程及自动启动入口、禁止消费者隐式在线查询、缺失资料只进入远端补漏队列。不要为了补缺在本地调用旧 `prpm_client.query_prpm` 或旧连续爬虫。是否被 DBP 拉黑、云厂商关联或触发 GFW 特征审查，无法由这段代码作 100% 保证，也无证据证明本方案会必然引发这些事件。

### 6.2 25 并发不能被描述为“几名普通学者”

每个线程成功后平均只休息 0.55 秒；按 11.3 秒响应假设，单机约 0.422 请求/秒，全集群约 **2.11 请求/秒、25 个请求可同时在途**。慢响应不代表后端空闲：它可能反映数据库开销、排队或跨区网络。增加 IP 不会增加站点总容量，也不能保证绕过按网段、ASN 或全站负载采取的限制。

现有三次重试不区分 429、503、404、解析异常、磁盘异常，且没有 Retry-After、集群熔断或动态降速。全部失败时最多会尝试 45,000 次请求。RFC 6585 定义了 429，服务端可以给出 Retry-After；客户端应识别它并配合降速，不能仅按 1/2 秒继续请求。[RFC 6585 §4](https://datatracker.ietf.org/doc/html/rfc6585#section-4)

推荐从一台一并发、少量有代表性的词开始，先验证正常页/无结果页/错误页与字段质量，再记录完整延迟分布及错误率；仅在得到稳定证据后逐步提高有限并发，并给集群设总请求预算。遇到明确限流或连续异常应暂停/熔断，不能通过增加 IP 持续施压。本次没有进行该在线试验，故无法给出 PRPM 的安全并发上限或封禁概率。

### 6.3 HTTP 服务与端口

`python3 -m http.server 8080` 默认绑定全部接口，提供当前目录的文件和目录列表；没有认证，当前命令也没有 TLS。它不是自动暴露整个 `/root`：当前服务根是 `/root/prpm_cache`。但以 root 运行和跟随符号链接会扩大错误配置的影响，公开目录也不应存任何密钥。[Python 3.12 HTTP 服务说明](https://docs.python.org/3.12/library/http.server.html)

脚本把服务输出重定向到 `/dev/null`，既不检查端口占用，也不确认进程活着；后台命令失败不会被这里的 `set -e` 可靠发现。8080 还需要云端防火墙和系统 UFW/nftables/iptables 两层允许，不能假定镜像默认值。部署时须从实际下载来源测试 TCP 和文件获取，并保留日志。[Vultr 双层防火墙排查](https://docs.vultr.com/support/products/network/how-do-i-troubleshoot-vultr-cloud-firewall-issues)

优先使用 SSH/SFTP 等受控下载，或将只读 HTTP 限定到明确来源；若仍用明文 HTTP，传输完整性应由可信渠道取得的 manifest/哈希验证。同一明文连接下载包和哈希只能帮助发现随机损坏，不能证明来源未被替换。不必为这次临时传输引入与目标无关的复杂系统。

## 7. 吞吐、时间、额度与费用

### 7.1 爬虫：能算条件估计，不能给真实完工保证

令 `N=15000`、总并发 `C=25`，每词有效占用线程的平均周期为 `S` 秒（含下载、解析、写盘、等待及重试）。均衡且站点未因并发变慢时：

```text
遍历速率 ≈ 3600 × C / S             （词/小时）
全量遍历时间 ≈ N × S / C / 3600     （小时）
```

**仅在每次完整请求都为 11.3 秒、无失败、忽略解析写盘等开销时**，加 0.3–0.8 秒 jitter 得到 `S=11.6–12.1`，理想范围约 **7,438–7,759 词/小时，1.93–2.02 小时**；取平均 jitter 为 **7,595 词/小时、1.975 小时**。11.3 秒在方案中还是 TTFB，完整下载和处理一般需要额外时间，因此这也不是可保证的上限工期。

方案的 9,000 词/小时要求每词周期仅 10 秒，在沿用 11.3 秒 TTFB 的假设下不成立。“集群实测 7,500–9,000”未找到测量日志、VPS 身份、状态码分布、有效记录计数或计时记录，必须撤回“实测”措辞。单线程 `3600/18` 也应为 200，而非文中的 196 词/小时。

| 假设平均每词周期 S | 25 路遍历速率 | 15,000 词遍历时间 | 含义 |
| --- | --- | --- | --- |
| 11.85 秒 | 7,595/小时 | 1.98 小时 | 理想、无重试 |
| 15.55 秒 | 5,788/小时 | 2.59 小时 | 仅作周期敏感性示例 |
| 20.55 秒 | 4,380/小时 | 3.43 小时 | 可能包含重试/等待，不代表 20 秒 TTFB 能在 15 秒设置下成功 |
| 30.55 秒 | 2,946/小时 | 5.09 小时 | 同上 |
| 48 秒 | 1,875/小时 | 8.00 小时 | 假定每次均恰好 15 秒超时，三次尝试加 1+2 秒退避；有效成功产量可能为零 |

最后一行不是严格最长运行时间：`urlopen(timeout=15)` 的 socket 超时不构成整个任务的硬截止时间，持续缓慢读入等情形仍可延长运行。再考虑节点失联、熔断、补漏和人工处置，当前方案**没有有限且可信的最坏完工时间**。状态中的遍历率也不能替代合格资料率。[urllib.request 超时参数](https://docs.python.org/3.12/library/urllib.request.html#urllib.request.urlopen)

### 7.2 Codex：20 路、5 词不等于已经有 1,000 词/小时

仓库没有 `src/concurrent_synthesizer.py`。现有 `batch_synthesizer.py` 只对 pilot 词表取串行 10 词批次，尚无 3,000 个五词任务的队列、20 路压测、重试台账或全量验证器。两批人工交付不能证明20路自动生产速度。

若每批 `B=5` 词，真正可持续并发 `P=20`，每批从准备到合格发布耗时 `t` 秒，理想生成吞吐为 `P×B×3600/t`。因此 **1,000 词/小时隐含每个五词批次平均 360 秒完成且通过门禁**：

| 五词批次耗时 t | 理想吞吐 | 15,000 词理想耗时 |
| --- | --- | --- |
| 3 分钟 | 2,000/小时 | 7.5 小时 |
| 6 分钟 | 1,000/小时 | 15 小时 |
| 12 分钟 | 500/小时 | 30 小时 |

这些是公式示例，不是实测承诺。实际还受账号限额、工具回合、重试、缓存准备、语言编辑和验收返工影响。本地命令只在日志里写 `gpt-6.1-sol / high`，没有显式传 `-m` 或推理档位，实际会依赖继承配置；不能从打印文字证明使用的模型。修正时须保持项目已定的 **`gpt-6.1-sol / high`**，不借审计换模型。

额度的确定部分是 **15,000/5=3,000 个初始批次**。每次 `codex exec` 可能有多个模型/工具回合，3,000 批不是 3,000 次固定计价的轻量消息。20 个进程共享账号可用额度，不能据并发数推断额度增加或免费运行保证。

设实测每批含全部回合的输入、缓存输入、输出及推理等用量为 `I,K,O,R`，应分别累计 `3000×(I,K,O,R)`，再加失败重试和验收成本，并避免按事件格式重复计算推理 token。仅作量级示例：若每批累计 8,000 输入、10,000 输出 token，则初始全量已有 2,400 万输入、3,000 万输出 token；**这些是假设，不能当本工程实测或账号扣额预测**。

官方说明额度依赖模型、上下文、推理、工具及缓存等因素，提示词长度无法单独预测；应读取账号当时的实际使用上限和重置时间。可用 `codex exec --json` 的完成事件记录用量，并用 `--output-schema` 请求结构化最终响应；仍须自行验证实际文件与词条内容。本次未查看用户计划/余额，也未使用付费 API 兜底。[官方额度说明](https://learn.chatgpt.com/docs/pricing)、[非交互输出与用量事件](https://learn.chatgpt.com/docs/non-interactive-mode)

### 7.3 是否会等待资料或死锁

若先等所有五包验收后再启动生产，是分阶段运行，总耗时近似“抓取 + 回收验收 + 生产”，即使理想 2 小时和 15 小时也约需 17 小时以上，不能称作始终无等待的同时流水线。

若生产与抓取同时启动，**平均抓取速率快不代表当前待编词的资料已经可用**。包只在整片结束后出现 READY；第 5 片卡住或正好包含当前批次，就可造成等待。本地数百个缓存也不是两小时缓冲，更何况其中有错误和未证实无词条记录。

当前串行消费者缺资料时直接返回 `found_in_prpm=false`，没有真正等待机制，因此不能声称已复现其“并发死锁”；实际风险是带缺失资料继续合成。未来若改为无限等待全缓存，缺片会永久阻塞。这属于无截止时间的外部依赖等待，尚无证据表明存在锁的循环等待。

调度应只从已验证 ready 队列取批次，缺失项转到单独队列，其余词继续；每词/批次设期限和终止状态。渐进交付可提供中间批次，但不能让消费者读取正在写的 JSON。集群平均速率只能用于容量规划，不是逐词准备就绪的门禁。

## 8. 一机故障、Windows 合并与生产内容门禁

### 8.1 一台宕机如何恢复

五台没有互相依赖，某台宕机不直接阻止另外四台完成各自分片，但其覆盖通常只剩 **12,000 词，不能称全量完成**。剩余节点不会自动认领故障片，机器本地部分产物若随销毁丢失也无法恢复。

统一补漏计算必须基于固定版本的词 ID，而非文件数：

```text
应覆盖集合 = 固定输入 manifest 中的全部词 ID
已终结集合 = 验证通过的 ok + 有证据的 verified_not_found
补漏集合   = 应覆盖集合 - 已终结集合
```

错误、损坏、未解析、无产物的词都留在补漏集合；词典确无词条另按合成材料政策处理，不能伪装成已获官方定义。识别缺口之后，给健康临时 VPS 显式分配 `missing.jsonl` 或故障片号，不靠改主机名猜测。故障机尚可访问时先回收已验证部分，再去重补漏；不可访问则重跑整片并按词 ID 去重。

在理想 11.85 秒周期下，另一台五线程机器补 3,000 词还需约 **1.975 小时**；不是自动几分钟补好。本地应仅负责计算清单和调度远端，不通过主力代理补抓。

### 8.2 大小写与真实 Windows 障碍

当前本地上传候选词全小写且无 NFC/casefold 冲突，**没有发现该 15,000 词中仅靠大小写不同造成覆盖的实例**。不能无证据宣称当前五片必有大小写冲突。不过 Kaikki 和未来词表可能保留不同写法；合并政策必须明确哪些写法属于同一检索键，保留原词头，不能只凭大小写自动合并词义。

本次已查到更确定的问题：第 **10,458** 项是 `con`。Linux 可生成 `con.json`，Windows 普通常规文件路径不能可靠使用该设备保留名，添加扩展名也不解除保留。Python 3.13 `ntpath.isreserved('con.json')` 返回 true。它位于第 4 片；该候选无 DBP/Kaikki 命中标签，也说明候选池不等于已清洗的 15,000 个马来语词条。[Microsoft 文件命名规则](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)

推荐以稳定安全 ID（例如前缀化哈希或 manifest 数字 ID）命名文件，词头保存在 JSON 内，由索引查找；或者统一采用经过验证的前缀/转义规则。必须一并调整现有所有 `raw/prpm_cache/{word}.json` 读取方。仅在解压时改名会让消费者找不到文件；也不能简单删掉 `con` 继续声称完整交付 15,000 词。

现有方案没有提供本地并行下载/解压代码，因此无从宣称其可靠。合格合并至少要做到：

1. 五包先保存到独立暂存目录，下载为 `.part`，处理 HTTP 失败、超时和重试；确认 READY、包大小与可信哈希。
2. 检查 manifest：输入哈希一致，片号恰为 1–5，分片边界、文件数与实际成员匹配。
3. 解压前拒绝绝对路径、`..`、符号链接/硬链接、设备文件、不安全 Windows 名称和重复映射；限制展开体积，实际目标须留在暂存目录。
4. 验证每个 JSON 的 UTF-8、结构、词 ID/词头、分片归属、抓取状态与内容哈希。重复但字节/语义不同的记录应显式报冲突，不能按“最后解压者获胜”。
5. 保护已有本地优质缓存，避免用远端 error/空解析覆盖它；对有差异的有效资料保留来源、时间与版本后按规则决策。最终一次性导入，产出缺口清单。
6. 全量覆盖与必要备份验收通过后，再销毁临时实例。

### 8.3 七维 Schema 和20路写入

`SCHEMA_TEMPLATE` 是给模型的文本示例，包含枚举说明和占位符，**不是可执行 JSON Schema**。当前调度函数仅看子进程返回码，未检查是否真的产生全部目标词文件、是否结构正确、是否保留了来源证据。`get_prpm_data` 在词根回退时无条件构造 `found_in_prpm=true`，不能证明派生词在词根条目中有对应义项/Jawi；缓存含 error 也可直接送入提示词。

合格产量应在外部验证后计算：七维字段与嵌套类型、词集合与批次/单词文件一致、来源词典归属、官方引文与编辑改述边界、Jawi/音节对应、派生与同形词、两个自然且包含目标形式的场景、未知词源不臆造。已有两批对未知词源和跨词条来源的明确处理必须保留，不能退回“每字段必须编一个答案”。需要允许证据不足与编辑复核状态。

20 个 Codex 进程若共享工作区、批次号、Git 索引和生产文件，可能互相覆盖，尤其旧批次 1、2 已有成果。推荐各 worker 消费独立输入包并写唯一暂存产物，由一个协调者验证、导入和提交；不要让20个代理共同维护状态页/索引或分别提交同一工作树。

方案称消费者“完全无需外网”，但现有命令显式允许 sandbox 网络访问，且 Codex 模型服务本身需要联网。准确目标应是**词典资料在本地、无 PRPM 在线查词依赖**，并以输入包和工具/网络限制落实，不能把提示词描述当成强制隔离。
