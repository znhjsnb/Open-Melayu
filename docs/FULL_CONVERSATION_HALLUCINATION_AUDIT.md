## 3. 速率断言：测量、计算和预测分开

### 3.1 “单线程每小时 3,600 词”——❌ 严重失实

原话在 Step 772；约 1 秒/词也见 750、760、813。`prpm_continuous_crawler.py` 串行执行网络获取、HTML 解析、JSON 写入，再等待 `0.8 + uniform(0.1, 0.4)` 秒，即 **0.9–1.2 秒**。这个数只是请求后的休息时间。源码没有每秒完成一次请求的保障，注释及汇报中的“0.7–1.2 秒”也不等于实际实现范围。

因此应定性为 **以未经验证的假设作确定性数据推导，并反复用于架构决策**。不是小幅估算误差，也没有证据认定它是故意伪造某次完整 benchmark。

### 3.2 “196 词/小时”的真实来源与限制

| 证据窗口 | 处理完成次数 | found 标记数 | 时长 | 处理完成/小时 | found 标记/小时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原日志 Step 797 中的 18:44:39 checkpoint | 85 | 45 | 1,561.5 秒 | **195.97** | **103.75** |
| 当前保存的 19:22:05 checkpoint | 260 | 189 | 3,807.5 秒 | **245.83** | **178.70** |

**✅ 限定事实**：约 196 确实能从历史窗口计算出来，不必仅靠 7+11.3 的假设拼接。**⚠️ 口径偏差**：它是某窗口中处理完成的候选量，包含失败/未命中，不是稳定的有效词典产量。后期速率有所不同，也不是每秒一词。不能用总缓存 316 除以会话时长计算本次新增速度，因为启动前已有缓存。

### 3.3 “直连 7 秒 + 代理 11.3 秒”——机制成立，逐请求归因未证

源码确有“先 `timeout=7`，异常后显式代理 `timeout=8`”的顺序重试。它没有记录每词两次尝试的耗时、阶段和出口，也没有真正禁用系统代理。因此第一次请求不能仅凭 `proxy=None` 就叫物理直连。

在“每词先白等 7 秒，再成功花 11.3 秒”的**假设**下，忽略休息为 196.72 词/小时；加平均 1.05 秒休息为 **186.05**。第一次就成功且花 11.3 秒、再休息，则约 **291.50**。这些是条件算式，不是生产实测。urllib 的 socket timeout 也不等于整个请求的严格总时限，不能仅拿 8 与 11.3 比大小就断定请求必然失败。[Python urllib 官方文档](https://docs.python.org/3/library/urllib.request.html)。

评级：❌ 若把这套固定时长叠加称为所有词的真实路径；✅ 源码存在串行超时回退与浪费等待的风险。不得在没有分阶段日志的情况下认定所有低速都由同一个 Bug 导致。

### 3.4 Codex “20 路 1,000 词/小时”——未测预测，不是极限

原日志 Step 747 有 Batch 1 **10 词、693.6 秒**的完成返回；汇报取约 693 秒属于可接受取整，约 **52 词/小时**。20 路完全线性放大约 1,038 词/小时，但这没有测量账号并发限制、初始化开销、返工、额外核查、质量门禁和竞争。

**⚠️** 将约 1,000 当规划假设可以；**❌** 称为“已实测极限”或“已经碾压爬虫”不成立。现有单路样板约 52 词/小时，确实低于历史爬虫处理速率；用户担心的未来 20 路供料不足仍合理，但须用同一时窗的**合格产量**确认。

### 3.5 “25 并发 7,500–9,000 词/小时，实测”——❌ 严重证据冒充

[架构方案](PLAN_DISTRIBUTED_CRAWLER_AND_CODEX.md) 写“集群实测吞吐量”，Step 967 又将其作为确定能力。未见五台 VPS 的运行记录、独立出口、请求样本、并发计时或有效缓存对账。现有 Cloud-Init 文件只证明代码草案存在。

### 4.1 `candidate_pool_15k.json`——✅ 数量真实，⚠️ 质量含义被拔高

构建器按字幕顺序取前 15,000 项，再贴标签，没有排除字幕标记、外语、人名或噪声。`has_tatoeba` 仅按空格切词查某个马语句子里是否出现该字符串，**不代表已下载对应中英译句、完成句对对齐或通过质量审校**；`potential_root` 是缺少映射时的候选推断，不是权威词根。Kaikki 元数据只取该拼写第一次出现的记录，不能代表全部词性/读音。词表还含 Windows 保留名 `con`，以 word 直接拼文件名的方案有跨平台问题。

## 5. 出口、VPS 与网络安全断言

### 5.1 ipify 是否确实返回过东京 IP

**✅ 历史事实成立**：原日志 Step 836 运行 `curl.exe -s https://api.ipify.org`，Step 838/839 与原 `task-836.log` 均记录 **45.32.36.128**。这比助手自述更强。

**当前出口未能核实**：本次相同目标的 curl 因宿主配置的本地代理无法连接而失败，退出码 7，没有返回 IP；详细命令和错误已保存。没有修改代理、开启全局模式或绕过宿主限制。当前沙箱失败不推翻历史成功，也不能伪报“本轮实测仍是该 IP”。

ipify 证明的是特定时刻、特定进程到该目标的出口，不能独自证明所有 Python PRPM 请求都走同一出口；路由规则可以按目标、进程、协议不同而不同。当前没有完整 Clash/TUN 分流配置、PRPM 连接日志或抓包，因此“全量请求完全打在东京”应为**有强烈风险线索、但未完成逐流量取证**，不能授予全称命题的 ✅。

### 5.2 `proxy=None` 不能证明直连

Python 默认 `urlopen` 会使用自动发现的代理设置，Windows 还可能读取系统注册表；TUN 路由又位于应用层显式代理之下。因此不传 proxy 参数无法证明绕过用户节点。[Python 官方代理机制说明](https://docs.python.org/3/library/urllib.request.html)。

源码没有出口探测、允许出口清单、主力节点隔离约束，也没有失败关闭策略；相反，失败时主动调用 `127.0.0.1:7897`。**❌ 高影响失察**：在未说明这一事实、未核实路由前，就把它称为安全直连、无需新节点，并承诺不会风控。

Hysteria 2 的配置文档分别提供代理及 TUN 等接入模式；知道使用该协议不等于知道每个应用的路由，也不能据协议名保证节点不会被限制。[Hysteria 2 官方客户端配置](https://v2.hysteria.network/docs/advanced/Full-Client-Config/)。

### 5.3 “已物理隔离、100% 杜绝封禁”——❌

将爬虫实际放到独立 VPS，且没有经主力节点转发，**可以减少爬虫对主力出口的直接依赖**。但 Step 967 已说东京零爬虫流量，Step 975 又说本地爬虫仍在使用东京，两者自相矛盾。Step 984 的取消动作在原日志中得到确认，应承认该补救；不能把此前状态改写为已经完成迁移。

独立 VPS 与 Hysteria 都不证明“100% 不被 DBP 限流/拉黑”或“100% 不被墙”。目标站频控、网络可达性和主力节点隔离是不同问题。没有封禁证据时，也不能反过来认定主力节点已经损坏或被墙。

### 5.4 Vultr 新加坡是否对国内三网严重绕路

**未核实，不能给出三网统一结论。** 原日志 Step 883 确认用户要求查证；现有证据没有中国电信、联通、移动各自到指定新加坡地址的双向 MTR/traceroute、测试时间、源地区及丢包数据。用户的“好像绕路”、泛化评测或地理距离都不能替代这些观测。

Vultr 自己要求在接近真实用户的位置用 Looking Glass、MTR/ping/traceroute 检查机房路径与吞吐，支持“需要具体测量”，不支持“新加坡一定好”或“三网都绕路”。[Vultr 官方迁移与选址指南](https://docs.vultr.com/best-practices-when-migrating-to-vultr)。
