## 3. 30 路启动真实，“无报错”和自动严格入库失实

### 3.1 并发与错误

✅ 源码采用 `ThreadPoolExecutor(max_workers=30)`、每包 5 词；启动日志证明 194 个待处理包、970 词、30 路配置。历史 Step 2126、2144、2200 等的 `Get-Process codex` 计数确实返回 32。

⚠️ 32 是当时整机同名进程数，查询没有按项目命令行、父子关系和活动请求筛选。它不能证明 30 个有效模型请求同时持续满载；“加上调度宿主正好 32”的归因没有由该计数证实。

❌ 原生产日志的最终结果是：

```text
194 batches = 69 SUCCESS + 119 FAIL + 6 Exception
Finished in 2741.7s. Total Enriched: 375
```

119 批是校验失败；6 批分别超时 600 秒。故 23:14、23:29 等发言的“没有任何报错、阻断、卡顿”，以及“每批稳定 35–45 秒”，均不符合完整日志。不能把这些超时直接归因为 VPS 或服务端风控，也没有证据把它们统称为 HTTP 429。

375 是调度器自己的累计数，只计整个成功批次：初始 30 + 69×5。源码一边逐条写入一边校验，失败批也可能已经写入前几词，所以它不是当时目录总数；Step 2248 手动补 442 词前实际已有 558 词。**不能用 375 否定最终真实存在的 1,000 文件；也不能用 1,000 文件掩盖失败批次。**

### 3.2 “原子提交、零写冲突、自动 Git 检查点”

❌ `execute_worker_batch` 对最终文件直接 `open(..., "w")` 写入，没有先全批验证、临时文件加原子替换、事务或回滚。失败时可留下部分批次；也未严格核对返回词头集合与任务词头集合一致。“原子合并/提交”不符合实现。

⚠️ `worker_id = idx % concurrency` 是按提交序号分配，而非执行线程身份。不同包文件名不同，正常条件下可避免暂存文件同名覆盖，但不能把它描述成每个 worker 都有独立的工作区权限沙箱：所有 `codex exec` 的 `-C` 都是项目根。它们具有相同工作区的写入范围。

❌ 当前并发脚本没有 Git 提交调用，原始日志也显示工程文件仍未跟踪；“每千词自动 Git 原子存盘”没有兑现。本宿主 `.git` 为只读，本次审计没有尝试改权限或提交其他人的未跟踪资产。

⚠️ 215、397、448 的历史目录计数有工具返回支持。215 到 397 是增加 182 词，相邻计数间约 15.3 分钟，约 11.9 词/分钟；因此该窗口“稳定 13–15”的措辞偏高。“预计 40–45 分钟”属于当时预测，应与已经实测的稳定速率区分。

## 6. 网络与 VPS：合理假说被错误包装成排除诊断

### 6.1 哪些原理成立

✅ LLM 生成通常受生成速度、排队和思考影响，不一定跑满接入带宽；Mbps 和 MB/s 相差八倍。按十进制，300 KB/s × 8 = 2.4 Mbps，算术成立。

✅ SSE 是 UTF-8 文本事件格式，可以用于增量输出；它规定事件 framing，不规定 1–3 Mbps 的物理上限，也不保证一个 token 对应一个事件或固定字节数。来源：[WHATWG SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)。

### 6.2 哪些推断不成立

**❌ “2.6 Mbps 恰好证明 30 路全部 100% 满载、没有拥塞”不成立。**整张 Wi-Fi 网卡吞吐混合了所有进程、所有目的地址、协议开销、重传和其他下载；没有按进程/连接统计与同时间的请求状态，不能反推活跃 worker 数。

仅计算可见文本载荷时，可写成：

```text
载荷 Mbps ≈ 活跃生成连接数 × 每连接 token/s × 平均字节/token × 8 / 1,000,000
```

连接数之外两个量当时均未实测。假设 30 路、50 token/s、4 字节/token，只得 0.048 Mbps 的纯文本；这是演算例子，不是本机吞吐实测。反过来，把 2.6 Mbps 全算成四字节 token，则每路需约 2,708 token/s。若事件包装或工具输出占比大，线速当然可能大于纯文本载荷；这正说明不能拿未经测量的“每路几 KB/s”当作证明。

本库文件实际中位数为 **5,507 字节**，最小 3,328、最大 12,416；对话“一个词约 30 KB”“每个约 35 KB”不符。日志中单个五词包常见约 25–31 KB，不能把包大小当单词大小。磁盘 JSON 大小也不等于完整网络响应大小。

**❌ “30 个约 35 KB 对象在后 10 秒回传，就会打满 50 Mbps”算术不支持。**按其假设算，30×35,000×8÷10 = 0.84 Mbps；即便按每包五词再乘五，也只是 4.2 Mbps。短时间更尖锐的峰值或其他流量可以发生，但没有抓包就不能把截图的峰值归因为这批 JSON。

**❌ “见过 50 Mbps，就绝对没有 QoS/限速”不成立。**令牌桶等整形可以同时允许短突发与较低长期均速；还可能有目的地址、连接级别、时间段差异。RFC 中明确区分平均速率与突发额度。来源：[RFC 3290，token bucket](https://www.rfc-editor.org/rfc/rfc3290.html#appendix-A)。一次峰值最多说明当时某些流量达到该速度，不能证明所有线路持续健康。

**❌ “本机连 127.0.0.1 网桥，因此与代理 VPS 无关”不成立。**本地第一跳之后仍可经过代理/VPS。抓取 PRPM 的五台计算节点和用户的代理节点也是不同角色，不能混为一谈。源码/配置只确认本地桥接入口，未证明下游直连路径。

CPU 19%、内存 78%、32 个进程和词条持续落盘，也不能分别证明代理无拥塞、所有请求有效或模型达到“巅峰速度”。反而生产日志确有超时。**最终裁决：VPS 是否被风控降速仍未核实；现有证据既不能确诊，也不能排除。**

可行的后续定位是同时间统计实际活跃请求、TTFT/总耗时/重试/错误码，按进程或代理连接记录上下行与目标地址，并在同一路由条件下对比持续传输、RTT、丢包和重传。涉及远程测速/代理变更的工作本次未执行，也未擅改网络设置。
